# 本地配方批次与放行

这是一个在本机运行的本地配方批次与放行台账。数据保存在调用方指定的本地目录中，
不同目录互相独立；程序退出后重新打开同一位置，已登记的数据及请求结果仍完整可查。

## 使用

```bash
go test ./...
```

### 打开台账

```go
s, err := release.Open("/path/to/data") // 目录不存在会自动创建；空目录得到空台账
defer s.Close()
```

已有台账文件但无法读取或解析时，`Open` 返回 `release.ErrCorruptData`，
不会当成空台账继续保存。零字节的台账文件同样按损坏处理（与“没有台账文件”
区分开）：无论文件原本就为空还是使用过程中被清空，都会返回 `ErrCorruptData`，
原文件保持零字节，不会补写成空台账，也不会凭此前的记录自动还原。每个批次绑定的配方编号与版本号必须共同指向一个
已登记的配方版本；任一批次缺少对应版本（同编号的其他版本不算），`Open`
同样返回 `ErrCorruptData`，错误信息包含该批次编号及其所需的配方编号、版本号。
每个已保存的配方版本都必须至少包含一种物料，与登记配方时的要求一致：
物料列表保存成空数组、`null` 或字段缺失都属于同一种损坏，即使名称、编号、
版本号齐全且台账内容能正常解析，`Open` 也返回 `ErrCorruptData`，错误信息
指出问题配方的编号与版本号并明确说明它没有物料；不会补造物料、不会删除
问题版本，也不会用同一配方编号下的其他完整版本顶替。这项检查覆盖所有已
保存版本，包括尚未被任何批次引用的版本；台账里另有正常配方与批次，或调用
方只查询正常记录，都不能绕过。采用空物料版本的批次即使份数为正、状态合法、
尚未投料，也不能以没有数量差额为由返回没有核对项的查询结果。没有登记任何
配方的空台账仍可正常使用，与存在一个没有物料的配方版本区分开。
读取每个已保存批次时，其状态必须精确对应 `draft`、`executing`、`closed`
三个值之一：状态缺失、为空、为 `null`，或保存成 `ready` 等其他字符串都不合法；
大小写不同（如 `Draft`）以及前后多了空格（如 ` draft `）也不会自动当成某个
合法状态。任一批次状态无法识别，`Open` 即返回 `ErrCorruptData`，错误信息
包含问题批次编号及实际读到的状态，状态为空或缺失时会明确说明为空或缺失；
不会根据有没有投料替它猜状态，不会补成草稿，也不会删除或跳过该批次继续返回
其他批次与配方——即使配方版本、计划份数正常，且尚未投料或投料数量已经吻合。
读取每个已保存批次时，其计划份数必须为正整数；按该批次实际绑定的配方版本
计算，每种物料的应投量（每份克数 × 计划份数）都必须能精确表示到千分之一克，
且不能超过 9223372036854775.807 克。任一批次份数为零或负数，或某物料应投量
超限，`Open` 同样返回 `ErrCorruptData`，错误信息包含批次编号与计划份数，
超限时还包含对应物料及绑定的配方编号、版本号。上限按每种物料分别判断，
多种物料的应投量相加超过上限不算非法，单种物料恰好等于上限仍可读取。
这项检查针对整份台账、覆盖草稿/执行中/已关闭全部状态，与本次查询哪个批次
无关。读取每个已保存批次的投料列表时，登记序号还必须与记录在列表中的位置
一致：第一条序号为 1，此后每条依次加 1。零、负数、漏号、重号、跳号，或
只调换记录位置却未同步序号（例如三条记录序号为 1、1、3 或 1、3、2），
即使物料归属与数量全部合法，`Open` 也返回 `ErrCorruptData`，错误信息包含
问题批次编号、该记录在列表中的位置、实际序号与应有序号；系统不会自行重排、
补号或删除投料。不同物料的投料共用所在批次的这一序列，不按物料另起编号；
不同批次各自从 1 开始。空投料列表不构成序号错误。投料时间只由调用方填写、
从不参与排序，时间相同或后一条早于前一条都不影响序号合法性。台账打开后文件
内容若被改坏，下一次查询或写入在重新读取时也会返回
`ErrCorruptData`，被拒绝的读取不会删除批次或补造配方，被拒绝的写入不留下
任何业务记录、不占用请求编号；恢复缺失的原配方版本、改为合法计划或修正登记
序号后重新打开即可继续使用。

打开台账以及后续每次查询、写入重新读取时，还要逐条核对已保存的成功配方登记
请求：原提交内容、保存的返回结果与台账中实际登记的版本三者必须一致——配方
编号、版本号、名称相同，物料项数、排列顺序、各项物料编号和每份克数也相符。
原请求登记的是 R1 的 v1，台账里即使另有完整的 R1/v2，也不能用 v2 的结果
顶替；两个版本名称相同或某些用量相同都不算同一版本。保存结果缺失、为 `null`、
为空对象、无法读成一份完整配方结果，原请求对应的版本不存在，或上述内容有
任何差异，`Open` 都返回 `ErrCorruptData`，错误信息指出问题请求编号，能确定
关联版本时还写明配方编号与版本号；不会删除请求、补造版本或重新登记。该检查
覆盖所有已保存的配方登记请求，即使该版本尚未被任何批次采用，或本次只查询、
写入别的正常记录，也不能绕过。每份克数按精确数值核对：原提交的 `1.000` 与
结果里的 `1`、`0.500` 与 `0.5` 代表相同用量，不因末尾的零不同误报损坏；但
请求内容的幂等匹配仍按原文比较，把原来的 `1.000` 改成 `1` 再提交仍返回
`ErrRequestConflict`。

打开台账以及后续每次查询、写入重新读取时，还要逐条核对已保存的成功创建批次
请求：保存的返回结果必须是原提交内容第一次创建成功时的那份批次结果——批次
编号、配方编号与版本号、计划份数都与原提交内容一致，配方名称取原提交所选的
已登记版本；结果必须仍是草稿、没有投料，并按原选版本的物料顺序完整列出数量
核对：每种物料的应投量为创建时每份克数乘以创建时份数，实投量为零，差额为
应投量的负值。另一批次的结果或同编号配方的其他版本，即使名称、物料和数量
相同，也不能顶替；原请求对应的批次和原选配方版本必须仍然存在。保存结果缺失、
为 `null`、为空对象、无法读成完整批次结果，原提交内容无法解析或不符合创建
要求，或上述对应关系不成立时，`Open` 都返回 `ErrCorruptData`，错误信息指出
问题请求编号，能确定批次时也包含批次编号；不会删除请求、补造批次，也不会
改写原文件。该检查覆盖所有已保存的创建批次请求：任何一条损坏都拒绝整份台账，
即使调用方只查询其他正常记录；被拒绝的写入不留下业务变更。正常的后续操作
不会被误判：草稿后来改选配方或调整份数，甚至已开始执行、追加投料并关闭，
保存的创建结果仍以最初提交为准；重复提交原创建请求继续返回首次结果，查询
继续显示当前批次。数量核对按精确数值比较：`1` 与 `1.000`、`0` 与 `0.000`、
`-1` 与 `-1.000` 分别视为相同数量。

打开台账以及后续每次查询、写入重新读取时，还要逐条核对已保存的成功草稿调整
请求：原调整请求对应的批次必须仍然存在，保存结果的批次编号必须与它一致；结果
必须为草稿且没有投料，结果采用的配方编号与版本要指向仍登记在案的版本、名称
与该版本一致、计划份数为正整数。原请求明确指定了新配方或新份数时，结果必须
反映指定的值，不能用其他版本或另一批次的结果顶替；配方编号与版本同时留空、
份数传 0 的沿用语义保持不变，沿用值只须符合完整性与数量规则，不要求与批次
当前计划相同。数量核对以结果采用的配方版本和份数为准，按该版本物料顺序完整
列出全部物料：应投量为每份克数乘以份数，实投量为零，差额为应投量的负值；
各物料应投量继续遵守现有精度与上限，不得遗漏、重复或混入其他版本的物料。
保存结果缺失、为 `null`、为空对象、无法解析，或上述对应关系不成立（含原提交
内容无法解析、原请求对应的批次不存在、结果采用的版本未登记）时，`Open` 都
返回 `ErrCorruptData`，错误信息指出问题请求编号和能确定的批次编号；不会删除
请求、补造批次或改写原文件。该检查覆盖所有已保存的草稿调整请求，即使调用方
正在查询或写入另一条正常记录，也不能跳过损坏结果继续使用；被拒绝的读取或
写入保留原文件、不补造结果、不删除请求，被拒绝的写入不留下业务变更、不占用
请求编号。批次后来再次调整，或已开始执行、追加投料并关闭，都属于批次现状，
不能使早先合法的草稿调整结果被误判为损坏：重复提交仍返回当次成功结果，查询
仍显示当前批次，不回退状态或改写投料。数量按精确数值比较：`1` 与 `1.000`、
`0` 与 `0.000`、`-1` 与 `-1.000` 分别视为相同数量。

打开台账以及后续每次查询、写入重新读取时，还要核对已保存的成功投料请求：保存
结果必须对应原请求批次中同序号的实际投料，且与原提交内容一致——物料编号、克数、
投料时间（同一时刻不区分时区写法）、登记人逐项相符；其他批次的同序号投料不能
顶替，原批次不存在时保存结果不能单独作为登记成功的依据。在此之上，两个不同的
成功投料请求不能指向同一批次的同一条投料登记：同一批次用两个不同请求编号登记
内容完全相同的投料，本应得到两个连续序号；若把第二次请求保存结果的序号改成
第一次的序号、其余内容保持一致，两个请求随后都会返回第一条投料——即使批次里
的两条投料都还在、累计数量也正确，这也不能被当作两次各自成功的登记。发现两个
请求（批次编号与登记序号相同）指向同一条投料时，`Open` 以及已打开对象后续
查询、写入的重新读取都返回 `ErrCorruptData`，错误信息说明两个请求指向了同一条
投料，并包含两个请求编号、批次编号和重复的登记序号；不会挑一个请求保留后继续，
不删除请求、不合并投料、也不替结果重新分配序号，原文件保持不变，被拒绝的写入
不留下业务记录、也不占用新请求编号。该检查覆盖全部已保存的投料请求，访问其他
正常批次也不能绕过；批次关闭后保存的投料请求同样受这项规则约束。不同批次可以
各有序号为 1 的投料，即使内容也相同，只要各请求指向各自的批次就不属于重复指向。
克数继续按精确数值核对（`1` 与 `1.000` 不判为差异），时间按同一时刻核对，请求
内容仍按原文匹配；已有投料没有对应请求记录时继续沿用现有读取规则，不要求补造
请求。

读取台账时，最外层的请求记录字段 `requests` 在同一份台账里只能出现一次。标准
JSON 对象解码遇到同名字段时会用后一段覆盖前一段：若最外层写了两次 `requests`，
后一段会把前一段整体覆盖——已有投料仍在，第一次登记保存的请求结果却可能消失，
调用方再提交原投料请求时会被当成新登记，平白增加一条投料。因此发现第二次出现
时，`Open` 以及已打开对象下一次查询、写入的重新读取都返回 `ErrCorruptData`，
不返回可继续使用的台账对象，错误信息明确指出最外层请求记录字段重复并写出
`requests`；不会选择其中一段、拼接两段或重建请求结果，原文件保持不变，被拒绝
的读取不返回局部结果，被拒绝的写入不增加投料、不改变批次状态，也不占用请求
编号。两段内容完全相同、各自保存不同请求编号，或其中一段为空对象或 `null`
（无论在前还是在后）都同样拒绝。字段名按解码后的实际名称判断：把其中字母写成
等价的 Unicode 转义（即在 `re` 后依次写反斜杠、字母 u、0、0、7、1 再接
`uests`，六个字符解码后是字母 q，整体仍是 `requests`）与直接写出的
`requests` 属于同一字段，现有读取本来就能识别的大小写写法（如 `Requests`、
`REQUESTS`）也不能用来让该字段第二次出现；但 `re-quests` 等近似名称不会命中，
请求记录等嵌套对象内部出现同名字段也不算最外层重复。只有一段 `requests` 时，
多条不同编号的成功请求仍可读取，同一编号与相同内容重复提交仍返回首次成功结果；
`requests` 缺失、为空对象或 `null`，在未出现或只出现一次时沿用原行为，仍可
正常使用。



### 登记投料并查看数量核对（完整流程）

下面这段说明从一个尚未使用的数据位置开始，在**同一个批次 B1** 上按文档顺序
连续完成：打开与释放台账、登记配方、创建批次、开始执行、登记投料、查询和
关闭。示例固定使用配方版本 R1/v1 与正整数份数 2；配方放 M1、M2 两种物料，
其中 M1 分两次投料，M2 暂不投料。每次写入使用不同请求编号，所有调用都处理
返回错误。代码可作为一整段直接运行，不需要从其他段落补齐变量或上下文。

```go
package main

import (
    "errors"
    "fmt"
    "log"
    "time"

    "github.com/bengzyyys/batch-release/release"
)

func main() {
    // 从一个尚未使用的数据位置开始：目录不存在会自动创建，空目录得到空台账。
    s, err := release.Open("./ledger-data")
    if err != nil {
        log.Fatalf("打开台账失败: %v", err)
    }
    defer func() {
        if err := s.Close(); err != nil { // 使用结束释放台账占用的文件锁
            log.Printf("关闭台账失败: %v", err)
        }
    }()

    cst := time.FixedZone("UTC+8", 8*60*60)

    // 1. 登记配方版本 R1/v1：M1 每份 250 克，M2 每份 40 克。
    //    同一版本内物料编号不可重复；已登记版本不可覆盖（ErrRecipeExists）。
    if _, err := s.RegisterRecipe("req-001", "R1", "v1", "红枣配方", []release.MaterialInput{
        {MaterialNo: "M1", Grams: "250"},
        {MaterialNo: "M2", Grams: "40"},
    }); err != nil {
        log.Fatalf("登记配方失败: %v", err)
    }

    // 2. 创建批次 B1：使用同一配方版本 R1/v1，固定正整数份数 2；创建后为草稿。
    if _, err := s.CreateBatch("req-002", "B1", "R1", "v1", 2); err != nil {
        log.Fatalf("创建批次失败: %v", err)
    }

    // 错误用法一：批次尚为草稿就登记投料。投料只能发生在开始执行之后，
    // 这里返回 release.ErrInvalidState，批次不增加任何投料，失败也不占用请求编号。
    if _, err := s.AddFeeding("req-bad-draft", "B1", "M1", "300",
        time.Date(2026, 10, 7, 8, 59, 0, 0, cst), "张三"); !errors.Is(err, release.ErrInvalidState) {
        log.Fatalf("草稿状态投料应返回 ErrInvalidState，实际: %v", err)
    }

    // 3. 开始执行：草稿 → 执行中。此后配方版本与计划份数固定，才允许登记投料。
    if _, err := s.StartBatch("req-003", "B1"); err != nil {
        log.Fatalf("开始执行失败: %v", err)
    }

    // 4. 登记投料（在开始执行之后、关闭之前）：M1 分两次登记，两次写入
    //    使用不同请求编号；克数按千分之一克精度给出，时间与登记人逐条记录。
    first, err := s.AddFeeding("req-004", "B1", "M1", "300",
        time.Date(2026, 10, 7, 9, 0, 0, 0, cst), "张三")
    if err != nil {
        log.Fatalf("登记第一次投料失败: %v", err)
    }
    if _, err := s.AddFeeding("req-005", "B1", "M1", "150.5",
        time.Date(2026, 10, 7, 9, 20, 0, 0, cst), "李四"); err != nil {
        log.Fatalf("登记第二次投料失败: %v", err)
    }
    // M2 暂不投料：它仍会出现在数量核对中，累计实投量为零。

    // 5. 执行中查询：查看每种物料的应投量、累计实投量与差额。
    executing, err := s.GetBatch("B1")
    if err != nil {
        log.Fatalf("执行中查询失败: %v", err)
    }
    printBatch(executing)

    // 6. 关闭批次：执行中 → 已关闭。关闭只确认已有投料，数量不足也允许关闭。
    closed, err := s.CloseBatch("req-006", "B1")
    if err != nil {
        log.Fatalf("关闭批次失败: %v", err)
    }
    printBatch(closed)

    // 错误用法二：关闭后换一个新请求编号追加投料。关闭后不能再追加，
    // 返回 ErrInvalidState，批次仍只有原来的两条投料，不增加第三条。
    if _, err := s.AddFeeding("req-007", "B1", "M1", "100",
        time.Date(2026, 10, 7, 10, 0, 0, 0, cst), "张三"); !errors.Is(err, release.ErrInvalidState) {
        log.Fatalf("关闭后追加投料应返回 ErrInvalidState，实际: %v", err)
    }

    // 原样重复提交已成功的投料请求 req-004（编号与批次、物料、克数、时间、
    // 登记人全部不变）：返回的仍是第一次登记的那条结果。这是按请求编号
    // 取回原记录，不是允许新增投料——批次始终只有序号 1、2 两条投料。
    replay, err := s.AddFeeding("req-004", "B1", "M1", "300",
        time.Date(2026, 10, 7, 9, 0, 0, 0, cst), "张三")
    if err != nil {
        log.Fatalf("重复提交原投料请求不应报错: %v", err)
    }
    if replay.Seq != first.Seq || replay.Grams != first.Grams || replay.Registrar != first.Registrar {
        log.Fatalf("重复提交应取回首次登记结果，实际得到: %+v", replay)
    }
}

// printBatch 打印批次状态、全部投料与逐物料数量核对。
func printBatch(b *release.BatchView) {
    fmt.Printf("批次 %s：状态 %s，配方 %s/%s，计划份数 %d，投料 %d 条\n",
        b.BatchNo, b.Status, b.RecipeNo, b.RecipeVersion, b.PlannedPortions, len(b.Feedings))
    for _, f := range b.Feedings {
        fmt.Printf("  投料 #%d：%s %s 克，%s，登记人 %s\n",
            f.Seq, f.MaterialNo, f.Grams, f.Time.Format("2006-01-02 15:04:05 MST"), f.Registrar)
    }
    for _, m := range b.Materials {
        fmt.Printf("  物料 %s：应投 %s 克，实投 %s 克，差额 %s 克\n",
            m.MaterialNo, m.RequiredGrams, m.ActualGrams, m.DifferenceGrams)
    }
}
```

投料时机只有一个窗口：**开始执行之后、关闭之前**。窗口之外的两次尝试
（示例中的 `req-bad-draft` 与 `req-007`）都返回 `release.ErrInvalidState`，
且都不增加投料。

执行中（第 5 步 `GetBatch`）与关闭后（第 6 步返回值及此后再次 `GetBatch`）
的关键查询结果如下，逐物料核对数量在关闭前后完全一致（单位：克）：

| 物料 | 应投量（每份克数 × 计划 2 份） | 累计实投量 | 实投 − 应投 |
| --- | --- | --- | --- |
| M1 | 500（250 × 2） | 450.5（300 + 150.5） | -49.5 |
| M2 | 80（40 × 2） | 0（未投料） | -80 |

- 执行中查询时状态为 `executing`：配方版本为 R1/v1（红枣配方）、计划份数 2；
  `Feedings` 保留两条独立记录，按登记顺序排列、不按物料合并——序号 1 为
  M1 300 克（2026-10-07 09:00:00 UTC+8，登记人张三），序号 2 为 M1 150.5 克
 （2026-10-07 09:20:00 UTC+8，登记人李四）。
- M1 的两次投料按千分之一克精度累计为 450.5 克，应投 500 克，差额 -49.5 克；
  M2 暂未投料仍然出现在核对结果中，应投 80 克、实投 0 克、差额 -80 克。
- 关闭后相比执行中**只有状态从 `executing` 变为 `closed`**：配方版本 R1/v1、
  计划份数 2、两条投料的顺序与数量、上表的逐物料核对数字全部保持一致；
  未投料的 M2 依旧列出，实投为零、差额为负。

**关闭只表示确认已登记的投料**：本例 M1 尚欠投 49.5 克、M2 完全未投，批次
仍可正常关闭。关闭不表示数量通过检查，也不代表已经放行；关闭后既不能追加
投料，也不能重新打开。

关闭后把已成功的投料请求**原样重复提交**（相同请求编号 `req-004` 与完全相同
的批次、物料、克数、时间、登记人），返回的仍是第一次登记的那条结果（序号 1、
300 克、张三）：这是按请求编号取回原记录，不是允许新增投料。只有换用新请求
编号才会进入状态校验并被 `ErrInvalidState` 拒绝（如 `req-007`）。

### 登记配方版本与草稿调整（其他写入入口）

上面的完整流程已经用到登记配方、创建批次、开始执行与关闭。配方的通用规则：
配方由配方编号与版本号共同识别，每个版本包含名称和至少一种物料，物料记录
编号和生产一份所需的克数（正数、最多三位小数）；同一版本内物料编号不可
重复，已登记的版本内容不可覆盖（`ErrRecipeExists`）。

另一个公开入口是草稿调整：批次开始执行前可以改计划份数或改选配方版本，
开始执行后两者固定。下面是独立于上面 B1 流程的另一个批次 B2 的例子，
不要把它接到 B1 的步骤之后：

```go
// 另一个独立场景：B2 在草稿阶段把份数从 10 调整为 20。
if _, err := s.CreateBatch("req-101", "B2", "R1", "v1", 10); err != nil {
    log.Fatalf("创建 B2 失败: %v", err)
}
if _, err := s.UpdateDraftBatch("req-102", "B2", "", "", 20); err != nil {
    log.Fatalf("调整 B2 失败: %v", err) // 配方编号与版本号留空表示不改配方，份数传 0 表示不改份数
}
```

批次状态机的三个阶段为：草稿（可调整、不可投料）→ 执行中（配方与份数固定、
可投料、可关闭）→ 已关闭（确认已有投料，不可追加投料或重新打开）。

### 投料的编号与顺序

完整流程中的 `AddFeeding` 就是投料入口：执行中可以分多次追加投料，物料必须
属于该批次绑定的配方版本，允许欠投或超投。投料按成功登记的先后顺序编号，
不按投料时间重排；同一批次不同物料共用这一序列、从 1 连续编号，不同批次
各自从 1 开始。即使两条投料时间相同，或后一条填写的时间早于前一条，登记
顺序与序号也保持不变（流程里 M1 的两次投料即保留为序号 1、2 两条记录）。
已登记的投料不能修改或删除；重新读取台账时若发现序号重号、跳号或与记录
位置不符，整份台账按损坏处理（见“打开台账”），不会自行重排或补号。

### 查询

```go
batch, err := s.GetBatch("B1") // 不存在时返回 release.ErrNotFound
recipe, err := s.GetRecipe("R1", "v1")
```

批次查询返回所用配方版本、计划份数、状态和全部投料，
并按物料逐项列出应投量（每份克数 × 计划份数）、累计实投量和实投减应投的差额；
没有投料的物料也会显示，超投不会抵消其他物料的欠投。
返回的视图是台账数据的副本，调用方修改不会影响台账。

### 请求编号与幂等

每次写入都带请求编号（第一个参数）。同一位置内：

- 相同编号 + 相同操作内容重复提交，返回第一次成功的结果，不新增批次或重复投料
  （即使批次已经关闭）；
- 相同编号用于其他操作或不同内容，返回 `release.ErrRequestConflict`；
- 失败不占用编号，也不留下部分记录或状态变化。

并发提交通过进程内互斥与文件锁（flock）串行化，同一请求同时到达只产生一次业务变更。

## 数量精度

克数以千分之一克为单位定点存储与计算（`100`、`100.5`、`0.001` 合法；
`0`、`-1`、`1.2345` 非法），份数为正整数，避免浮点误差。

同一批次内，每种物料的累计实投量上限为 9223372036854775.807 克
（按物料分别判断，其他物料的投料量不参与）；追加后恰好等于上限仍可成功，
超过则 `AddFeeding` 返回 `ErrInvalidInput`，不保存本次投料，
失败不占用请求编号。

每种物料按计划计算的应投量（每份克数 × 计划份数）同样以该值为上限、
按物料分别判断：创建或调整草稿批次导致某物料应投量超限时，该次提交
返回 `ErrInvalidInput` 且整体不落盘；已保存批次的份数或应投量不合法
则属于数据损坏，下一次读取返回 `ErrCorruptData`（见“打开台账”）。
