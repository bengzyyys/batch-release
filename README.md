# 本地配方批次与放行

这是一个在本机运行的本地配方批次与放行台账。数据保存在调用方指定的本地目录中，
不同目录互相独立；程序退出后重新打开同一位置，已登记的数据及请求结果仍完整可查。

## 使用

```bash
go test ./...
```

### 打开台账

```go
s, err := release.Open("/path/to/data") // 目录不存在会自动创建；空目录得到空台账
defer s.Close()
```

已有台账文件但无法读取或解析时，`Open` 返回 `release.ErrCorruptData`，
不会当成空台账继续保存。零字节的台账文件同样按损坏处理（与“没有台账文件”
区分开）：无论文件原本就为空还是使用过程中被清空，都会返回 `ErrCorruptData`，
原文件保持零字节，不会补写成空台账，也不会凭此前的记录自动还原。每个批次绑定的配方编号与版本号必须共同指向一个
已登记的配方版本；任一批次缺少对应版本（同编号的其他版本不算），`Open`
同样返回 `ErrCorruptData`，错误信息包含该批次编号及其所需的配方编号、版本号。
每个已保存的配方版本都必须至少包含一种物料，与登记配方时的要求一致：
物料列表保存成空数组、`null` 或字段缺失都属于同一种损坏，即使名称、编号、
版本号齐全且台账内容能正常解析，`Open` 也返回 `ErrCorruptData`，错误信息
指出问题配方的编号与版本号并明确说明它没有物料；不会补造物料、不会删除
问题版本，也不会用同一配方编号下的其他完整版本顶替。这项检查覆盖所有已
保存版本，包括尚未被任何批次引用的版本；台账里另有正常配方与批次，或调用
方只查询正常记录，都不能绕过。采用空物料版本的批次即使份数为正、状态合法、
尚未投料，也不能以没有数量差额为由返回没有核对项的查询结果。没有登记任何
配方的空台账仍可正常使用，与存在一个没有物料的配方版本区分开。
读取每个已保存批次时，其状态必须精确对应 `draft`、`executing`、`closed`
三个值之一：状态缺失、为空、为 `null`，或保存成 `ready` 等其他字符串都不合法；
大小写不同（如 `Draft`）以及前后多了空格（如 ` draft `）也不会自动当成某个
合法状态。任一批次状态无法识别，`Open` 即返回 `ErrCorruptData`，错误信息
包含问题批次编号及实际读到的状态，状态为空或缺失时会明确说明为空或缺失；
不会根据有没有投料替它猜状态，不会补成草稿，也不会删除或跳过该批次继续返回
其他批次与配方——即使配方版本、计划份数正常，且尚未投料或投料数量已经吻合。
读取每个已保存批次时，其计划份数必须为正整数；按该批次实际绑定的配方版本
计算，每种物料的应投量（每份克数 × 计划份数）都必须能精确表示到千分之一克，
且不能超过 9223372036854775.807 克。任一批次份数为零或负数，或某物料应投量
超限，`Open` 同样返回 `ErrCorruptData`，错误信息包含批次编号与计划份数，
超限时还包含对应物料及绑定的配方编号、版本号。上限按每种物料分别判断，
多种物料的应投量相加超过上限不算非法，单种物料恰好等于上限仍可读取。
这项检查针对整份台账、覆盖草稿/执行中/已关闭全部状态，与本次查询哪个批次
无关。读取每个已保存批次的投料列表时，登记序号还必须与记录在列表中的位置
一致：第一条序号为 1，此后每条依次加 1。零、负数、漏号、重号、跳号，或
只调换记录位置却未同步序号（例如三条记录序号为 1、1、3 或 1、3、2），
即使物料归属与数量全部合法，`Open` 也返回 `ErrCorruptData`，错误信息包含
问题批次编号、该记录在列表中的位置、实际序号与应有序号；系统不会自行重排、
补号或删除投料。不同物料的投料共用所在批次的这一序列，不按物料另起编号；
不同批次各自从 1 开始。空投料列表不构成序号错误。投料时间只由调用方填写、
从不参与排序，时间相同或后一条早于前一条都不影响序号合法性。台账打开后文件
内容若被改坏，下一次查询或写入在重新读取时也会返回
`ErrCorruptData`，被拒绝的读取不会删除批次或补造配方，被拒绝的写入不留下
任何业务记录、不占用请求编号；恢复缺失的原配方版本、改为合法计划或修正登记
序号后重新打开即可继续使用。

打开台账以及后续每次查询、写入重新读取时，还要逐条核对已保存的成功配方登记
请求：原提交内容、保存的返回结果与台账中实际登记的版本三者必须一致——配方
编号、版本号、名称相同，物料项数、排列顺序、各项物料编号和每份克数也相符。
原请求登记的是 R1 的 v1，台账里即使另有完整的 R1/v2，也不能用 v2 的结果
顶替；两个版本名称相同或某些用量相同都不算同一版本。保存结果缺失、为 `null`、
为空对象、无法读成一份完整配方结果，原请求对应的版本不存在，或上述内容有
任何差异，`Open` 都返回 `ErrCorruptData`，错误信息指出问题请求编号，能确定
关联版本时还写明配方编号与版本号；不会删除请求、补造版本或重新登记。该检查
覆盖所有已保存的配方登记请求，即使该版本尚未被任何批次采用，或本次只查询、
写入别的正常记录，也不能绕过。每份克数按精确数值核对：原提交的 `1.000` 与
结果里的 `1`、`0.500` 与 `0.5` 代表相同用量，不因末尾的零不同误报损坏；但
请求内容的幂等匹配仍按原文比较，把原来的 `1.000` 改成 `1` 再提交仍返回
`ErrRequestConflict`。

打开台账以及后续每次查询、写入重新读取时，还要逐条核对已保存的成功创建批次
请求：保存的返回结果必须是原提交内容第一次创建成功时的那份批次结果——批次
编号、配方编号与版本号、计划份数都与原提交内容一致，配方名称取原提交所选的
已登记版本；结果必须仍是草稿、没有投料，并按原选版本的物料顺序完整列出数量
核对：每种物料的应投量为创建时每份克数乘以创建时份数，实投量为零，差额为
应投量的负值。另一批次的结果或同编号配方的其他版本，即使名称、物料和数量
相同，也不能顶替；原请求对应的批次和原选配方版本必须仍然存在。保存结果缺失、
为 `null`、为空对象、无法读成完整批次结果，原提交内容无法解析或不符合创建
要求，或上述对应关系不成立时，`Open` 都返回 `ErrCorruptData`，错误信息指出
问题请求编号，能确定批次时也包含批次编号；不会删除请求、补造批次，也不会
改写原文件。该检查覆盖所有已保存的创建批次请求：任何一条损坏都拒绝整份台账，
即使调用方只查询其他正常记录；被拒绝的写入不留下业务变更。正常的后续操作
不会被误判：草稿后来改选配方或调整份数，甚至已开始执行、追加投料并关闭，
保存的创建结果仍以最初提交为准；重复提交原创建请求继续返回首次结果，查询
继续显示当前批次。数量核对按精确数值比较：`1` 与 `1.000`、`0` 与 `0.000`、
`-1` 与 `-1.000` 分别视为相同数量。在此之上，两个不同的成功创建批次请求
不能指向同一个批次：同一批次的首次创建请求若被保存到两个不同的请求编号下，
两份内容和返回结果各自单独核对都能通过，随后两个编号都会被当成各自创建
成功——即使两个提交完全相同、保存结果都是合法的草稿结果、配方份数与数量
核对全都一致，这也不能被当作两次各自成功的创建；两个提交采用不同配方版本
或份数、各自保存结果仍符合对应提交时，同样不能解释成两次合法创建。发现
两个不同请求编号的成功创建请求原提交指向同一批次编号时，`Open` 以及已打开
对象后续查询、写入的重新读取都返回 `ErrCorruptData`，错误信息说明同一批次
有多个成功创建请求，并包含批次编号与发生冲突的两个请求编号；不会挑一个
请求保留后继续，不删除请求、不合并、不改号，也不重新创建批次来消除矛盾，
原文件保持不变，被拒绝的写入不留下业务记录、不改变批次现状，也不占用新
请求编号。该检查覆盖全部已保存的创建批次请求，查询其他正常批次或配方也
不能绕过；批次后来调整过配方份数、已开始执行、投料并关闭，都不能拿批次
现在的计划筛掉早期请求而掩盖重复创建。不同批次各有自己的成功创建请求，
即使采用同一配方与份数也正常使用；草稿调整、开始执行和关闭请求与创建
请求引用同一批次属于正常操作，不纳入重复创建判断；已有批次没有保存创建
请求时继续沿用原来的读取要求，不要求补造请求。

打开台账以及后续每次查询、写入重新读取时，还要逐条核对已保存的成功草稿调整
请求：原调整请求对应的批次必须仍然存在，保存结果的批次编号必须与它一致；结果
必须为草稿且没有投料，结果采用的配方编号与版本要指向仍登记在案的版本、名称
与该版本一致、计划份数为正整数。原请求明确指定了新配方或新份数时，结果必须
反映指定的值，不能用其他版本或另一批次的结果顶替；配方编号与版本同时留空、
份数传 0 的沿用语义保持不变，沿用值只须符合完整性与数量规则，不要求与批次
当前计划相同。数量核对以结果采用的配方版本和份数为准，按该版本物料顺序完整
列出全部物料：应投量为每份克数乘以份数，实投量为零，差额为应投量的负值；
各物料应投量继续遵守现有精度与上限，不得遗漏、重复或混入其他版本的物料。
保存结果缺失、为 `null`、为空对象、无法解析，或上述对应关系不成立（含原提交
内容无法解析、原请求对应的批次不存在、结果采用的版本未登记）时，`Open` 都
返回 `ErrCorruptData`，错误信息指出问题请求编号和能确定的批次编号；不会删除
请求、补造批次或改写原文件。该检查覆盖所有已保存的草稿调整请求，即使调用方
正在查询或写入另一条正常记录，也不能跳过损坏结果继续使用；被拒绝的读取或
写入保留原文件、不补造结果、不删除请求，被拒绝的写入不留下业务变更、不占用
请求编号。批次后来再次调整，或已开始执行、追加投料并关闭，都属于批次现状，
不能使早先合法的草稿调整结果被误判为损坏：重复提交仍返回当次成功结果，查询
仍显示当前批次，不回退状态或改写投料。数量按精确数值比较：`1` 与 `1.000`、
`0` 与 `0.000`、`-1` 与 `-1.000` 分别视为相同数量。

打开台账以及后续每次查询、写入重新读取时，还要核对已保存的成功投料请求：保存
结果必须对应原请求批次中同序号的实际投料，且与原提交内容一致——物料编号、克数、
投料时间（同一时刻不区分时区写法）、登记人逐项相符；其他批次的同序号投料不能
顶替，原批次不存在时保存结果不能单独作为登记成功的依据。在此之上，两个不同的
成功投料请求不能指向同一批次的同一条投料登记：同一批次用两个不同请求编号登记
内容完全相同的投料，本应得到两个连续序号；若把第二次请求保存结果的序号改成
第一次的序号、其余内容保持一致，两个请求随后都会返回第一条投料——即使批次里
的两条投料都还在、累计数量也正确，这也不能被当作两次各自成功的登记。发现两个
请求（批次编号与登记序号相同）指向同一条投料时，`Open` 以及已打开对象后续
查询、写入的重新读取都返回 `ErrCorruptData`，错误信息说明两个请求指向了同一条
投料，并包含两个请求编号、批次编号和重复的登记序号；不会挑一个请求保留后继续，
不删除请求、不合并投料、也不替结果重新分配序号，原文件保持不变，被拒绝的写入
不留下业务记录、也不占用新请求编号。该检查覆盖全部已保存的投料请求，访问其他
正常批次也不能绕过；批次关闭后保存的投料请求同样受这项规则约束。不同批次可以
各有序号为 1 的投料，即使内容也相同，只要各请求指向各自的批次就不属于重复指向。
克数继续按精确数值核对（`1` 与 `1.000` 不判为差异），时间按同一时刻核对，请求
内容仍按原文匹配；已有投料没有对应请求记录时继续沿用现有读取规则，不要求补造
请求。

读取台账时，最外层的请求记录字段 `requests` 在同一份台账里只能出现一次。标准
JSON 对象解码遇到同名字段时会用后一段覆盖前一段：若最外层写了两次 `requests`，
后一段会把前一段整体覆盖——已有投料仍在，第一次登记保存的请求结果却可能消失，
调用方再提交原投料请求时会被当成新登记，平白增加一条投料。因此发现第二次出现
时，`Open` 以及已打开对象下一次查询、写入的重新读取都返回 `ErrCorruptData`，
不返回可继续使用的台账对象，错误信息明确指出最外层请求记录字段重复并写出
`requests`；不会选择其中一段、拼接两段或重建请求结果，原文件保持不变，被拒绝
的读取不返回局部结果，被拒绝的写入不增加投料、不改变批次状态，也不占用请求
编号。两段内容完全相同、各自保存不同请求编号，或其中一段为空对象或 `null`
（无论在前还是在后）都同样拒绝。字段名按解码后的实际名称判断：把其中字母写成
等价的 Unicode 转义（即在 `re` 后依次写反斜杠、字母 u、0、0、7、1 再接
`uests`，六个字符解码后是字母 q，整体仍是 `requests`）与直接写出的
`requests` 属于同一字段，现有读取本来就能识别的大小写写法（如 `Requests`、
`REQUESTS`）也不能用来让该字段第二次出现；但 `re-quests` 等近似名称不会命中，
请求记录等嵌套对象内部出现同名字段也不算最外层重复。只有一段 `requests` 时，
多条不同编号的成功请求仍可读取，同一编号与相同内容重复提交仍返回首次成功结果；
`requests` 缺失、为空对象或 `null`，在未出现或只出现一次时沿用原行为，仍可
正常使用。



### 登记配方版本

配方由配方编号与版本号共同识别，每个版本包含名称和至少一种物料，
物料记录编号和生产一份所需的克数（正数、最多三位小数）。

```go
// 独立片段：与下一节的连续流程不在同一数据位置，请求编号也刻意区分，
// 避免读者把两段示例按顺序放进同一台账时发生请求编号冲突。
recipe, err := s.RegisterRecipe("req-recipe-1", "R9", "v1", "配方九", []release.MaterialInput{
    {MaterialNo: "M1", Grams: "100"},
    {MaterialNo: "M2", Grams: "0.5"},
})
```

同一版本内物料编号不可重复；已登记的版本内容不可覆盖（`ErrRecipeExists`）。

### 登记投料并查看数量核对（连续流程）

下面这段示例从一个尚未使用的数据位置开始，在同一个批次 `B1` 上按顺序完成
打开与释放台账、登记配方、创建批次、开始执行、登记投料、查询和关闭。配方只
登记一个版本 `R1/v1` 并全程使用它，计划份数固定为正整数 4；配方含两种物料：
`M1` 分两次投料，`M2` 暂不投料。每次写入使用不同的请求编号；所有调用都处理
返回错误。整段代码可直接运行，不需要读者补齐上下文。

```go
package main

import (
	"errors"
	"fmt"
	"log"
	"os"
	"time"

	"github.com/bengzyyys/batch-release/release"
)

func main() {
	// 从一个尚未使用的数据位置开始：目录不存在会自动创建，空目录得到空台账。
	// 实际使用时把这里换成固定路径即可；重新打开同一位置，数据仍完整可查。
	dataDir, err := os.MkdirTemp("", "ledger-walkthrough-")
	if err != nil {
		log.Fatalf("准备数据位置失败: %v", err)
	}
	store, err := release.Open(dataDir)
	if err != nil {
		log.Fatalf("打开台账失败: %v", err)
	}
	defer func() {
		if err := store.Close(); err != nil { // 释放台账占用的文件锁
			log.Fatalf("释放台账失败: %v", err)
		}
	}()

	// 1. 登记配方版本 R1/v1：每一份用 M1 50 克、M2 12.5 克。
	recipe, err := store.RegisterRecipe("req-001", "R1", "v1", "混合配方", []release.MaterialInput{
		{MaterialNo: "M1", Grams: "50"},
		{MaterialNo: "M2", Grams: "12.5"},
	})
	if err != nil {
		log.Fatalf("登记配方失败: %v", err)
	}
	fmt.Printf("已登记配方 %s/%s（%s），物料 %d 种\n", recipe.RecipeNo, recipe.Version, recipe.Name, len(recipe.Materials))

	// 2. 用同一配方版本创建批次 B1，固定的正整数计划份数：4 份。新批次为草稿。
	batch, err := store.CreateBatch("req-002", "B1", "R1", "v1", 4)
	if err != nil {
		log.Fatalf("创建批次失败: %v", err)
	}
	fmt.Printf("批次 %s 已创建，状态=%s，计划份数=%d\n", batch.BatchNo, batch.Status, batch.PlannedPortions)

	// 3. 开始执行：草稿 → 执行中。投料必须发生在这一步之后。
	batch, err = store.StartBatch("req-003", "B1")
	if err != nil {
		log.Fatalf("开始执行失败: %v", err)
	}
	fmt.Printf("批次 %s 状态=%s\n", batch.BatchNo, batch.Status)

	// 4. 登记投料：物料 M1 分两次投，M2 暂不投料。
	//    每次写入使用不同的请求编号；克数、投料时间和登记人都明确给出。
	t1 := time.Date(2026, 10, 7, 9, 30, 0, 0, time.UTC)
	feeding1, err := store.AddFeeding("req-004", "B1", "M1", "120", t1, "张三")
	if err != nil {
		log.Fatalf("第一次登记投料失败: %v", err)
	}
	fmt.Printf("投料 #%d：%s %s 克，%s 登记\n", feeding1.Seq, feeding1.MaterialNo, feeding1.Grams, feeding1.Registrar)

	t2 := time.Date(2026, 10, 7, 10, 15, 30, 0, time.UTC)
	feeding2, err := store.AddFeeding("req-005", "B1", "M1", "80.250", t2, "李四")
	if err != nil {
		log.Fatalf("第二次登记投料失败: %v", err)
	}
	// 台账按千分之一克定点保存，成功结果去掉末尾多余的 0：提交 80.250 显示 80.25。
	fmt.Printf("投料 #%d：%s %s 克，%s 登记\n", feeding2.Seq, feeding2.MaterialNo, feeding2.Grams, feeding2.Registrar)

	// 5. 执行中查询：两次登记保留为两条投料，数量按千分之一克精度累计。
	executing, err := store.GetBatch("B1")
	if err != nil {
		log.Fatalf("执行中查询失败: %v", err)
	}
	printBatch("执行中查询结果：", executing)

	// 6. 关闭批次：执行中 → 已关闭。关闭只确认已有投料：即使 M2 完全未投、
	//    数量并不吻合也允许关闭。关闭不表示数量通过检查，也不表示已经放行。
	closed, err := store.CloseBatch("req-006", "B1")
	if err != nil {
		log.Fatalf("关闭批次失败: %v", err)
	}
	printBatch("关闭返回结果：", closed)

	// 7. 关闭后再次查询：配方版本、计划份数、投料顺序与核对数量都不变，
	//    只有状态变为已关闭。
	afterClose, err := store.GetBatch("B1")
	if err != nil {
		log.Fatalf("关闭后查询失败: %v", err)
	}
	printBatch("关闭后查询结果：", afterClose)

	// 错误用法一：草稿状态登记投料。B2 刚创建仍是草稿，投料返回 ErrInvalidState，
	// 不增加投料。
	if _, err := store.CreateBatch("req-007", "B2", "R1", "v1", 4); err != nil {
		log.Fatalf("创建批次 B2 失败: %v", err)
	}
	if _, err := store.AddFeeding("req-008", "B2", "M1", "10", t1, "张三"); !errors.Is(err, release.ErrInvalidState) {
		log.Fatalf("草稿状态投料应返回 ErrInvalidState，得到 %v", err)
	}
	b2, err := store.GetBatch("B2")
	if err != nil {
		log.Fatalf("查询 B2 失败: %v", err)
	}
	fmt.Printf("草稿投料被拒绝：B2 投料条数=%d（未增加投料）\n", len(b2.Feedings))

	// 错误用法二：关闭后用新请求编号追加投料。返回 ErrInvalidState，不增加投料。
	if _, err := store.AddFeeding("req-009", "B1", "M2", "50", t2, "王五"); !errors.Is(err, release.ErrInvalidState) {
		log.Fatalf("关闭后追加投料应返回 ErrInvalidState，得到 %v", err)
	}
	b1Again, err := store.GetBatch("B1")
	if err != nil {
		log.Fatalf("关闭后查询 B1 失败: %v", err)
	}
	fmt.Printf("关闭后追加被拒绝：B1 投料条数=%d（未增加投料）\n", len(b1Again.Feedings))

	// 关闭后用原请求编号、原样重复提交已成功的投料请求：返回第一次登记的那条
	// 记录（这里是 #2）。这是取回原记录，不是允许新增投料。
	replay, err := store.AddFeeding("req-005", "B1", "M1", "80.250", t2, "李四")
	if err != nil {
		log.Fatalf("原样重放已成功的投料请求应返回首次结果: %v", err)
	}
	fmt.Printf("原样重放取回投料 #%d：%s %s 克，%s 登记\n", replay.Seq, replay.MaterialNo, replay.Grams, replay.Registrar)
	finalView, err := store.GetBatch("B1")
	if err != nil {
		log.Fatalf("最终查询 B1 失败: %v", err)
	}
	fmt.Printf("重放后 B1 投料条数=%d（取回原记录，不新增投料）\n", len(finalView.Feedings))
}

// printBatch 打印批次状态、全部投料与逐物料数量核对。
func printBatch(title string, b *release.BatchView) {
	fmt.Println(title)
	fmt.Printf("  批次=%s 配方=%s/%s（%s） 计划份数=%d 状态=%s\n",
		b.BatchNo, b.RecipeNo, b.RecipeVersion, b.RecipeName, b.PlannedPortions, b.Status)
	fmt.Println("  投料登记（按登记顺序）：")
	for _, f := range b.Feedings {
		fmt.Printf("    #%d %s %s 克 投料时间=%s 登记人=%s\n",
			f.Seq, f.MaterialNo, f.Grams, f.Time.Format(time.RFC3339), f.Registrar)
	}
	fmt.Println("  数量核对（应投量 / 累计实投量 / 差额=实投-应投，单位克）：")
	for _, m := range b.Materials {
		fmt.Printf("    %s: %s / %s / %s\n", m.MaterialNo, m.RequiredGrams, m.ActualGrams, m.DifferenceGrams)
	}
}
```

#### 执行中的查询结果

两次投料之后、关闭之前，`GetBatch("B1")` 返回状态 `executing`、配方 `R1/v1`、
计划份数 4，投料按成功登记的先后保留为两条（投料时间不参与排序）：

| 序号 | 物料 | 本次克数 | 投料时间 | 登记人 |
| --- | --- | --- | --- | --- |
| 1 | M1 | 120 | 2026-10-07T09:30:00Z | 张三 |
| 2 | M1 | 80.25 | 2026-10-07T10:15:30Z | 李四 |

逐物料数量核对（应投量 = 每份克数 × 4；差额 = 累计实投 − 应投）：

| 物料 | 应投量（克） | 累计实投量（克） | 差额（克） |
| --- | --- | --- | --- |
| M1 | 200（50×4） | 200.25（120 + 80.250） | 0.25 |
| M2 | 50（12.5×4） | 0（暂不投料） | -50 |

没有投料的 `M2` 仍然出现：实投量为零，差额为应投量的负值 -50；`M1` 的两次
登记始终保留为两条投料，不做合并。数量按千分之一克精度定点累计：提交的
`80.250` 与结果中显示的 `80.25` 是同一数量，120 + 80.250 精确累计为 200.25。

#### 关闭后的查询结果

关闭后再查 `B1`，配方版本（`R1/v1`）、计划份数（4）、投料顺序与上面的核对
数量全部保持一致，只有状态从 `executing` 变为 `closed`：两条投料仍是 #1、#2，
`M1` 仍是 200 / 200.25 / 0.25，`M2` 仍是 50 / 0 / -50。

关闭的含义是**确认批次上已有的投料记录**：即使本例中 `M2` 完全未投、整体
数量并不吻合，执行中的批次也允许关闭。关闭不是“数量通过检查”，也不代表
“已经放行”；关闭后不能追加投料，也不能重新打开。

#### 投料时机的两个错误用法

投料只允许发生在开始执行之后、关闭之前。下面两种写法都返回
`release.ErrInvalidState`（可用 `errors.Is` 判断），且都不增加投料：

```go
// 1) 草稿状态登记投料：B2 尚未开始执行，返回 ErrInvalidState，B2 仍无投料。
_, err = store.AddFeeding("req-008", "B2", "M1", "10", t1, "张三")
fmt.Println(errors.Is(err, release.ErrInvalidState)) // true

// 2) 关闭后用新请求编号追加投料：B1 已关闭，返回 ErrInvalidState，仍是两条投料。
_, err = store.AddFeeding("req-009", "B1", "M2", "50", t2, "王五")
fmt.Println(errors.Is(err, release.ErrInvalidState)) // true
```

失败的提交不占用请求编号，也不改变批次状态。另外，关闭后用**原请求编号、
原样**重复提交此前已成功的投料请求（示例中的 `req-005`，物料、克数原文、
投料时间与登记人完全一致），仍会返回第一次登记的结果（序号 2 的那条
80.25 克记录）：这是按幂等规则**取回原记录**，不是允许在关闭后新增投料，
批次中的投料条数与累计实投量都不因重放而变化。

### 批次状态机与草稿调整

批次生命周期为 草稿（`draft`）→ 执行中（`executing`）→ 已关闭（`closed`）。
上一节已在 `B1` 上演示创建、开始执行、投料与关闭的完整连续流程；草稿阶段
独有的“调整份数 / 改选配方版本”在下面这个独立片段中用另一个批次 `B3` 演示
（同样需要先登记配方并打开台账，这里省略与上节相同的准备代码）：

```go
batch, err := s.CreateBatch("req-101", "B3", "R1", "v1", 10) // 草稿，份数为正整数
if err != nil {
	log.Fatal(err)
}
batch, err = s.UpdateDraftBatch("req-102", "B3", "", "", 20) // 草稿可改份数/配方
if err != nil {
	log.Fatal(err)
}
batch, err = s.StartBatch("req-103", "B3") // 草稿 → 执行中
if err != nil {
	log.Fatal(err)
}
batch, err = s.CloseBatch("req-104", "B3") // 执行中 → 已关闭
if err != nil {
	log.Fatal(err)
}
```

`UpdateDraftBatch` 的新配方编号与版本号同时留空表示不改配方，新份数传 0
表示不改份数；非草稿状态调整返回 `ErrInvalidState`。开始执行后计划份数与
配方版本固定；只有执行中的批次可以登记投料与关闭，关闭确认已有投料、不要求
数量吻合；关闭后不能追加投料或重新打开（投料的完整连续示例见上一节）。

投料按成功登记的先后顺序编号，不按投料时间重排；同一批次不同物料共用这一
序列、从 1 连续编号，不同批次各自从 1 开始。即使两条投料时间相同，或后一条
填写的时间早于前一条，登记顺序与序号也保持不变。已登记的投料不能修改或删除；
重新读取台账时若发现序号重号、跳号或与记录位置不符，整份台账按损坏处理
（见“打开台账”），不会自行重排或补号。

### 查询

```go
batch, err := s.GetBatch("B1") // 不存在时返回 release.ErrNotFound
recipe, err := s.GetRecipe("R1", "v1")
```

批次查询返回所用配方版本、计划份数、状态和全部投料，
并按物料逐项列出应投量（每份克数 × 计划份数）、累计实投量和实投减应投的差额；
没有投料的物料也会显示，超投不会抵消其他物料的欠投。
返回的视图是台账数据的副本，调用方修改不会影响台账。
执行中与关闭后查询的完整字段示例见上一节“登记投料并查看数量核对”。

### 请求编号与幂等

每次写入都带请求编号（第一个参数）。同一位置内：

- 相同编号 + 相同操作内容重复提交，返回第一次成功的结果，不新增批次或重复投料
  （即使批次已经关闭；上一节已演示关闭后原样重放 `req-005` 只取回首次登记的
  投料记录，不增加投料）；
- 相同编号用于其他操作或不同内容，返回 `release.ErrRequestConflict`；
- 失败不占用编号，也不留下部分记录或状态变化。

并发提交通过进程内互斥与文件锁（flock）串行化，同一请求同时到达只产生一次业务变更。

## 数量精度

克数以千分之一克为单位定点存储与计算（`100`、`100.5`、`0.001` 合法；
`0`、`-1`、`1.2345` 非法），份数为正整数，避免浮点误差。

同一批次内，每种物料的累计实投量上限为 9223372036854775.807 克
（按物料分别判断，其他物料的投料量不参与）；追加后恰好等于上限仍可成功，
超过则 `AddFeeding` 返回 `ErrInvalidInput`，不保存本次投料，
失败不占用请求编号。

每种物料按计划计算的应投量（每份克数 × 计划份数）同样以该值为上限、
按物料分别判断：创建或调整草稿批次导致某物料应投量超限时，该次提交
返回 `ErrInvalidInput` 且整体不落盘；已保存批次的份数或应投量不合法
则属于数据损坏，下一次读取返回 `ErrCorruptData`（见“打开台账”）。
